# Протокол WebSocket

Эндпоинт: `/ws`. Текстовые кадры, JSON. Каждое сообщение — конверт:

```json
{ "t": "<тип>", "d": { ...данные } }
```

Версия протокола: **5** (`internal/protocol.Version`, `SBNet.PROTO` в клиенте).
Меняется только при несовместимом изменении сообщений. Добавление необязательных полей —
не несовместимое изменение: в 0.9.0 версию не поднимали, хотя добавились `room.ping`, номер `seq`
и поле `ping` у участника лобби. В 0.11 подняли до 4 — убраны клиентский зонд `ping` (клиент →
сервер) и ответ `pong` (сервер → клиент), а это уже удаление, а не добавление. В 0.15.1 подняли
до 5 — из зонда `ping` убрано поле `ms`, измеренная задержка переехала в отдельный `self.ping`.

Полезные константы и структуры — в `internal/protocol/protocol.go`, он же источник истины.

## Клиент → сервер

| Тип | Данные | Когда |
|---|---|---|
| `hello` | `{token?, nick, build, proto}` | первое сообщение после подключения; **пустой `nick`** у игрока без аккаунта — просьба выдать имя («Играть гостем»), сервер отвечает случайным `welcome.nick` |
| `pong` | `{seq}` | ответ на зонд `ping` от сервера (см. ниже): по нему сервер считает задержку |
| `room.create` | `{mode, arena, gameMode?, campaign?, difficulty?, visibility?}` | создать комнату, стать хостом |
| `room.join` | `{code, section?}` | войти по коду (четыре цифры `1234`; старый префикс `SNB-` отбрасывается); можно и в комнату с идущим матчем. `section` — раздел, из которого игрок вошёл: комната другого раздела отдаст `wrong_section` |
| `room.slot` | `{team: "A"\|"B", index}` | занять слот команды (в PvE только `"A"`) |
| `room.role` | `{role}` | выбрать бойца |
| `room.config` | `{mode, arena, gameMode?, campaign?, difficulty?, visibility?}` | хост меняет настройки комнаты |
| `room.ready` | `{ready}` | отметить готовность; когда готовы все люди в комнате, матч стартует сам |
| `room.kick` | `{playerId}` | хост выгоняет |
| `room.start` | — | хост стартует матч независимо от готовности, пустые слоты займут боты |
| `room.leave` | — | выйти из комнаты |
| `room.list` | `{section: "pvp"\|"pve", page}` | запросить страницу списка комнат и подписаться на её обновления |
| `room.unlist` | — | снять подписку (игрок ушёл с экрана списка) |
| `match.join` | — | войти в идущий матч за бойца своего слота в комнате |
| `match.leave` | — | выйти из боя, оставшись в комнате: место сохраняется, бойца ведёт бот |
| `input` | `{kind, x, y, power?}` | ввод в матче, пробрасывается в `sim.applyInput` как есть |
| `training` | `{on, mode?, arena?, role?}` | клиент играет тренировку с ботами; сервер в ней не участвует, отметка нужна только админке |
| `chat.send` | `{text, scope?}` | сообщение в чат: `scope` пуст — общий чат меню, `"room"` — чат комнаты; текст чистится, мат маскируется, ≤ 300 символов, не чаще 1 раза в 1.5 с на игрока |
| `chat.del` | `{id, scope?}` | удалить сообщение чата: своё, а по роли модерации — и чужое (правила ниже) |
| `nick.set` | `{nick}` | сменить ник аккаунта; гостю отвечает `no_account` (он меняет ник переподключением) |
| `tutorial.done` | `{id}` | урок пройден; от гостя игнорируется молча |
| `tutorial.sync` | `{ids}` | слить прогресс устройства с аккаунтом (объединение, не замена) |

`input.kind`: `move`, `chargeStart`, `aim`, `throw` (с `power` 0..1), `cancelCharge`, `special`.
Координаты в системе арены 900×560. Клиент шлёт `aim`/`move` не чаще ~15 раз в секунду.
Сенсорный клиент направления стиков тоже превращает в точки арены (`web/client/intent.js`),
поэтому серверу неважно, мышь это или стик.

## Сервер → клиент

| Тип | Данные | Когда |
|---|---|---|
| `welcome` | `{token, playerId, nick, build, sim, proto, draining?, resume, rank?, account?, auth?, tutorial?}` | ответ на `hello`; `resume` ∈ `menu\|room\|match` — куда вернуться; `rank` — роль модерации; `account` — аккаунт вошедшего, `auth` — включённые способы входа, `tutorial` — пройденные уроки аккаунта |
| `error` | `{code, msg?}` | ошибка обработки; коды ниже |
| `reload` | — | клиент устарел (другая сборка или протокол): `location.reload()` |
| `drain` | `{active, inSeconds?}` | сервер готовится к перезапуску (баннер) |
| `room.state` | `{code, hostId, mode, arena, gameMode?, campaign?, difficulty?, visibility, players[], inMatch, readyCount, lastWinner?}` | полное состояние лобби при любом изменении; у участника есть `ping?` |
| `room.left` | `{code?: "kicked"}` | вы вышли/вас выгнали |
| `room.list` | `{section, page, pages, total, rooms[]}` | страница списка комнат; пока игрок подписан, сервер сам присылает её заново при изменениях |
| `room.match` | `{code, timeLeftMs, slots[]}` | состояние идущего матча для тех, кто сидит в лобби этой комнаты; уходит при изменении |
| `match.start` | `{matchId, mode, arena, gameMode?, players[], yourId, tickRate, roomCode?}` | матч начался, вы переподключились или вошли за бойца своего слота |
| `match.roster` | `{players[]}` | состав матча изменился: кто-то занял место бота или вышел |
| `snapshot` | `{tick, s: <снапшот sim.js>, e?: [события шага], cd?: мс до старта}` | каждый тик (20/с) |
| `match.end` | `{winner: "A"\|"B"\|"", yourTeam, reason, roomCode?}` | `reason` PvP ∈ `ko\|timeout\|abandoned\|shutdown`, PvE ∈ `cleared\|wiped\|objective\|expired` |
| `ping` | `{seq}` | зонд задержки раз в 2 с; клиент обязан ответить `pong` с тем же номером. Самого числа зонд не несёт |
| `self.ping` | `{ms}` | задержка самого адресата; уходит при изменении, в любом состоянии игрока. `0` — неизвестна |
| `room.ping` | `{code, pings: [{id, ping}]}` | задержки участников лобби; уходит при изменении, отдельно от `room.state` |
| `account` | `{account, tutorial?}` | состояние аккаунта изменилось: ник или прогресс обучения |
| `online` | `{n}` | число игроков на сервере; шлётся при каждом изменении |
| `chat.msg` | `{id, nick, text, ts, scope?}` | одно сообщение чата: общий — всем подключённым, `scope: "room"` — только участникам комнаты; `ts` — unix-мс |
| `chat.history` | `{messages[], scope?}` | последние сообщения чата (за час): общая приходит сразу после `welcome`, история комнаты — при входе в неё; обе — после смены чьей-либо роли |
| `chat.del` | `{id, scope?}` | сообщение удалено — убрать его у аудитории этого чата |
| `chat.clear` | — | историю общего чата очистила админка (чаты комнат не трогает) |
| `rank` | `{rank}` | роль модерации этого игрока изменилась |

`room.state.players[]`: `{id, nick, team, index, role, host, connected, ready, inMatch, rank?}`.
`match.start.players[]` и `match.roster.players[]`: `{id, nick, team, index, role, bot, botLevel?, rank?}` —
`index` вместе с `team` привязывает бойца к слоту комнаты.

**`rank` и `role` — разные вещи.** `role` — класс бойца («Раннер», «Танк»). `rank` — роль
модерации: `""` (обычный игрок), `"moderator"`, `"admin"`. Она выдаётся по IP из админки, влияет на
цвет ника (админ — золотой, модератор — фиолетовый) и на права в чате. В составе матча `rank`
фиксируется на момент старта, в `room.state` и `chat.msg` он всегда актуальный.
`room.match.slots[]`: `{team, index, nick, role, bot, hp, koed}` — `bot: true` значит, что бойца
сейчас ведёт бот: слот свободен или его человек ушёл в лобби.
`room.list.rooms[]`: `{code, section, gameMode?, campaign?, mode, arena, humans, bots, capacity,
inMatch, visibility, hostNick, ageMs, joinable, needCode?}`. Комнаты идут по времени создания,
старые первыми, по 25 на страницу. У закрытой комнаты `code` пустой и `needCode: true` — иначе
список сам выдавал бы то, что защищает код.
Слот комнаты и боец матча — одно и то же. Вошедший в комнату (в ожидании или во время матча)
получает свободный слот, `room.slot` меняет его на другой свободный, а `match.join` сажает игрока
за бойца именно этого слота: `match.start.yourId` у него равен id бойца, а не id сессии. Ник в
снапшоте остаётся ботовским (симуляция не умеет переименовывать бойцов), поэтому имена в
интерфейсе клиент берёт из состава матча. Выход из боя (`match.leave`) оставляет игрока в комнате,
и место держится за ним, пока он в комнате: ушёл из комнаты или истекла сессия — слот свободен.

`snapshot.cd` > 0 — идёт отсчёт перед началом матча: симуляция стоит, `input` сервером не
применяется, клиент рисует «3, 2, 1». Поля нет — матч идёт.

Формат `snapshot.s` и `snapshot.e` определяет `sim.js` (`snapshot(state)` и события `step`),
см. [SIM_CONTRACT.md](SIM_CONTRACT.md). Сервер их не разбирает и передаёт как есть.

## Коды ошибок

`rename_cooldown` (ник аккаунта меняли меньше десяти минут назад), `no_account` (действие
только для вошедшего),
`bad_message`, `bad_version`, `not_allowed`, `bad_nick`, `nick_profanity` (в нике мат —
отдельный код, чтобы клиент назвал настоящую причину), `nick_taken` (ник занят до перезапуска
сервера, см. «Ники»), `room_not_found`, `room_full`,
`room_limit`, `busy` (сначала выйдите из комнаты/матча), `draining`, `bad_mode`,
`bad_arena`, `bad_role`, `bad_gamemode`, `bad_slot`, `bad_code`, `too_many_tries`
(не больше пяти неудачных попыток кода с адреса в минуту — защита от перебора закрытых комнат),
`slot_taken`, `no_slots`, `chat_flood` (сообщения в чат чаще раза в 1.5 с),
`wrong_section` (код от комнаты другого раздела; попытка тратит тот же лимит, что и неверный код —
иначе отличимый ответ подсказывал бы, что код существует), `banned` (адрес заблокирован через
админку: соединение закрывается, сама страница открывается как всем), `server_full`, `internal`.

## Сессия и переподключение

`welcome.token` клиент хранит в localStorage и присылает в следующем `hello`. Сервер помнит
игрока `ReconnectTTL` (60 с) после обрыва. Если пришёл `hello` с токеном, пока старое
соединение ещё живо, старое закрывается с причиной `replaced by new connection`
(две вкладки одного браузера = один игрок).

## Аккаунты

Аккаунт — вход по Яндекс ID. Он не отменяет гостевой режим: гость по-прежнему называет ник и
играет, и для него ничего не изменилось. Аккаунт нужен тому, кто хочет одно и то же имя,
прогресс обучения и роль модерации на телефоне и на компьютере, независимо от адреса.

Сессия (`welcome.token`) остаётся как была — она про «здесь и сейчас». Аккаунт живёт дольше:
он лежит на диске (`internal/accounts`) и опознаётся **подписанной httpOnly-кукой** `sb_acc`,
которую браузер сам прикладывает к HTTP-апгрейду `/ws`. Поэтому сервер знает игрока ещё до
`hello`, а формат `hello` менять не пришлось: у вошедшего ник берётся из аккаунта, а `hello.nick`
игнорируется.

Вторая кука, `sb_acc_hint`, — тот же id аккаунта, но читаемая клиентом и без секретов. Она нужна
ровно для одного: заметить, что вход или выход случился **в другой вкладке**, и переподключиться.
Узнать об этом по сокету нельзя — он открыт от прежнего лица.

HTTP-ручки: `GET /auth/yandex` (уводит к провайдеру), `GET /auth/yandex/callback` (принимает код,
ставит куки, возвращает в игру), `POST /auth/logout`. Пустой `SNOWBRAWL_YANDEX_CLIENT_ID` —
ручек нет вовсе, а клиент не показывает кнопку: включённые способы входа он узнаёт из
`welcome.auth` и из `<meta name="auth">` в самой странице (кнопка нужна на экране ника, где
сокета ещё нет).

Версию протокола аккаунты не подняли: все изменения аддитивны — новые необязательные поля в
`welcome` и новые типы сообщений. Старая вкладка до них не доходит, её отсекает проверка `build`.

## Ники

Ник уникален на весь сервер, но броней две. **За аккаунтом** имя закреплено навсегда: оно лежит
в `accounts.json` и освобождается только собственным переименованием (`nick.set`, не чаще раза в
десять минут). **За гостем** — как раньше, до перезапуска сервера и по адресу с сессией. Ник,
закреплённый за чужим аккаунтом, гостю не выдаётся; ник, под которым прямо сейчас играет гость,
не отдаётся аккаунту — иначе в лобби оказались бы два одинаковых имени.

Имена, которые выдаёт сервер, — вида «Ловкий Пингвин» (`protocol.RandomNick`, прилагательное плюс
существительное). Их получают двое: гость, нажавший «Играть гостем» и не вводивший имени вовсе,
и аккаунт, которому не подошло имя из профиля Яндекса (короткое, с запрещёнными символами,
матерное или занятое) — такому ставится флаг `account.nickAuto`, и клиент сразу предлагает выбрать
ник. Если все полторы тысячи комбинаций заняты, в ход идёт «Игрок NNNN». Вход из-за ника не падает
никогда.

Сравнение идёт по нормализованной форме (`protocol.NickKey`):
регистр вниз, латиница и похожие на буквы цифры сводятся к кириллице, `ё`→`е`, `й`→`и`, пробел,
`_` и `-` игнорируются. Цифры и повторы букв значимы: `Игрок2` и `Игрок5` — разные имена, иначе
игрок получал бы отказ, на который не может ничего ответить.

Гостевая бронь живёт в памяти, на диск не пишется и привязана к адресу **и** к токену сессии:
перезагрузка страницы и смена сети ник не отнимают. Оговорки, которые стоит знать: за одним NAT
ник виден как «свой» для всех, а гость, вернувшийся с нового адреса позже `ReconnectTTL`, своего
ника не получит — поэтому текст отказа мягкий («занят: другим игроком, чужим аккаунтом или вами
с другого адреса»). Бан адреса гостевую бронь отпускает. Аккаунтам всё это не касается: их имя
на диске и переезжает с игроком.

## Задержка (ping)

Механизм один. Сервер раз в 2 с шлёт `ping{seq}`, клиент обязан ответить `pong{seq}`; по ответу
считается RTT, сглаженный пополам, и публикуется с точностью до миллисекунды. Одно и то же число
идёт в три места: в лобби (поле `ping` у участника плюс отдельный диффингованный `room.ping`),
в админку и самому игроку отдельным `self.ping` — им живёт индикатор рядом с точкой соединения.
Своего зонда у клиента нет: два независимых замера давали в углу экрана и в лобби разные числа,
а верить измерению клиента нельзя — его видят все участники лобби и админ.

`self.ping` и `room.ping` уходят на одном тике хаба, поэтому индикатор в углу и своя строка
в составе лобби меняются одним кадром. До 0.15.1 измеренное число ехало полем `ms` в теле
следующего зонда, а зонд несёт прошлое измерение — угол отставал от лобби на целый цикл, до 2 с.
Отдельное сообщение нужно ещё и потому, что `room.ping` приходит только сидящим в лобби, а угол
виден и в меню, и в бою, и в оффлайн-тренировке. Клиент рисует своё число только из `self.ping`
и свою запись в `room.ping` игнорирует: один источник — расхождение невозможно.

Ноль или отсутствие поля значит «ещё не измерена» — у ботов, у только что зашедших и у тех, кто
потерял связь. До 0.11 значение округлялось до 10 мс с зоной нечувствительности 12 мс, чтобы
сводка админки не менялась сама по себе (на этом стоит диффинг SSE-потока). Зона оказалась шире
шага, и число застревало; теперь мигание таблиц лечится на своём месте — админка обновляет
изменившиеся ячейки, а не пересобирает таблицу целиком.

## Чаты

Панель в главном меню одна (по умолчанию раскрыта), внутри две вкладки: **Комната** — чат
комнаты, он появляется только у её участников, и **Общий** — чат на весь сервер. Вне комнаты
открыт общий чат; при входе в комнату клиент переключается на её чат, при выходе — обратно.
У вкладки, куда пришло сообщение, пока она не открыта, горит точка; на свёрнутой панели число
непрочитанных — сумма по обеим. Удалённое сообщение из счётчика уходит сразу.

Область чата несёт поле `scope`: пусто (поля нет) — общий чат, `"room"` — чат комнаты. Оно есть
в `chat.send`, `chat.msg`, `chat.history` и `chat.del`. `chat.send` со `scope: "room"` от игрока
вне комнаты отклоняется с `not_allowed`. Антифлуд общий на оба чата: пауза считается по игроку,
а не по чату.

### Общий чат

Один чат на весь сервер. Сообщения лежат в памяти hub, живут `SNOWBRAWL_CHAT_TTL` (по умолчанию час) и теряются при перезапуске — БД в проекте нет.
Буфер обрезается до 300 сообщений. `chat.msg` рассылается всем подключённым независимо от
того, открыта ли у них панель; клиент показывает счётчик непрочитанных. Ник берётся из сессии.

Мат маскируется звёздочками (`internal/censor`), само сообщение доходит; матерный ник при входе
отклоняется с `bad_nick`.

`chat.msg.pid` — id автора: по нему клиент понимает, что сообщение его, и рисует мусорку.
Права на удаление проверяет сервер, роль автора берётся **актуальная**, а не та, что была при
отправке:

- автор удаляет своё сообщение;
- «Админ» — любое;
- «Модератор» — только сообщения обычных игроков (ни админов, ни других модераторов).

Удаление по неизвестному id — не ошибка: сообщение могло выпасть из буфера по TTL. Кнопка
«Очистить чат» в админке стирает историю у всех (`chat.clear`); нумерация сообщений при этом не
сбрасывается, иначе новые id столкнулись бы с теми, что клиенты держат в разметке. Чаты комнат
`chat.clear` не трогает.

### Чат комнаты

`chat.msg` со `scope: "room"` получают только участники комнаты — и те, кто в лобби, и те, кто
сейчас в матче: слот комнаты остаётся за игроком, значит и чат остаётся. Буфер — 100 сообщений
на комнату, TTL тот же, что у общего чата, но живёт он не дольше самой комнаты: буфер удаляется
вместе с ней (см. `dropRoom` в `internal/hub/hub.go`). Вошедший получает `chat.history` со
`scope: "room"` — и при входе в комнату, и при переподключении. Права на удаление и маскировка
мата — те же, что в общем чате. Нумерация сообщений сквозная для всех чатов: id уникален.

## Лимиты

Сессия одна на игрока: подключение с тем же токеном закрывает прежнее соединение кодом 1008
и причиной `replaced by new connection`. Клиент на эту причину **не переподключается** — иначе
две вкладки вышибают друг друга по кругу; он показывает выбор «играть здесь». Текст причины
менять нельзя, не поправив `web/client/net.js`.

Сообщение ≤ 4 КБ; 60 сообщений/с на соединение (всплеск 120). Сверх лимита **отбрасываются
только `input` вида `move` и `aim`** — они идут потоком и идемпотентны; всё остальное
(`chargeStart`, `throw`, `special`, чат, `hello`) обрабатывается всегда, потому что теряет
состояние: отброшенный `throw` оставил бы бойца в вечном замахе. Соединение закрывается (1008,
причина `rate limit`) при устойчивом превышении втрое — от 180 сообщений/с при запасе 600, то
есть при флуде, а не у активного игрока. Очередь отправки 256 сообщений, при переполнении
соединение закрывается.
