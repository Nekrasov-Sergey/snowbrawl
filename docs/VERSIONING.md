# Версионирование и релизы

Три независимые версии:

| Что | Где задаётся | Кто видит | Когда менять |
|---|---|---|---|
| **Сборка** (`build`) | git-тег `vX.Y.Z`, вшивается в бинарник `-X main.buildVersion` | подвал меню, `/api/version`, `/healthz`, логи, `hello`/`welcome` | каждый релиз, автоматически |
| **Симуляция** (`sim`) | `SIM_VERSION` в `web/sim/sim.js` | подвал меню, админка, логи старта | при изменении правил игры |
| **Протокол** (`proto`) | `internal/protocol.Version` и `SBNet.PROTO` в `web/client/net.js` | `hello`/`welcome`, `/api/version` | только при несовместимом изменении сообщений |

Клиент вшит в бинарник, поэтому клиент и сервер всегда одной сборки. Старая вкладка после
деплоя присылает в `hello` старый `build` и получает `reload`.

## Релиз

Ветка `main` защищена ruleset'ом `protect-main`: прямой push запрещён, нужен PR с зелёным check
`test`. Включены **rebase-only merge**, «Require linear history» и автоудаление ветки после влития.
Merge-коммитов в истории больше не бывает.

Порядок ниже — рабочая инструкция для агента и для второго разработчика. Агент выполняет её только
по явной команде о доставке («сделай релиз», «влей и задеплой», «доведи до игроков»); такая команда
разрешает все шаги до пуша тега включительно. Без неё изменения остаются незакоммиченными.

1. **Ветка от свежего main.**

   ```bash
   git fetch --tags origin
   git checkout -b feat/<kebab> origin/main   # или fix/<kebab>
   ```

2. **Изменения.** Если их заметит игрок — новый раздел в `CHANGELOG.md` сразу с номером версии и
   датой. Раздел `[Unreleased]` не используем. Правки, не доезжающие до сервера (документация, CI),
   в CHANGELOG не попадают.

3. **Проверки:** `make test`, `gofmt -l .` (пусто), `make lint`, `node --check` для изменённых JS.

4. **Коммит и push.** Сообщение по-русски в повелительном наклонении.

   ```bash
   git commit -am "Добавь …"
   git push -u origin feat/<kebab>
   ```

5. **PR** через GitHub MCP (`mcp__github__create_pull_request`). `gh` не установлен, токена GitHub в
   окружении нет — других путей не искать.

6. **Дождаться check `test`** (`mcp__github__pull_request_read` с `get_check_runs`). Красный —
   починить и запушить в ту же ветку, **максимум две попытки**; если падает третий раз, остановиться
   и доложить, что именно не проходит.

7. **Если ветка отстала от main** (merge заблокирован линейной историей):

   ```bash
   git fetch origin && git rebase origin/main
   git push --force-with-lease
   ```

   Кнопкой «Update branch» и `update_pull_request_branch` не пользоваться: они вливают main в ветку
   merge-коммитом. `--force` без `--force-with-lease` запрещён — рядом работает второй разработчик.

8. **Merge** через `mcp__github__merge_pull_request` с `merge_method: "rebase"`. Значение по
   умолчанию (`merge`) репозиторий отклонит. Если MCP недоступен — остановиться и попросить
   пользователя нажать merge в вебе, затем продолжить со следующего шага.

9. **Синхронизация и уборка.**

   ```bash
   git checkout main && git pull --ff-only
   git rev-parse HEAD          # должен совпасть с sha из ответа merge
   git branch -d feat/<kebab>  # удалённую GitHub снёс сам
   git remote prune origin
   ```

10. **Нужен ли тег.** Если изменения тронули только `docs/**`, `README.md`, `CHANGELOG.md`,
    `CLAUDE.md`, `.github/**` — тега нет, работа закончена: тег перезапускает сервер и рвёт
    соединения игроков без всякой пользы. Всё остальное, включая `deploy/**`, тегируется: файлы
    выкладки доезжают на VPS только через `scp` внутри `release.yml`.

11. **Номер версии.** Взять максимальный из `git tag --sort=-v:refname | head -1` и увеличить по
    таблице ниже. rc-теги не используем.

    ```bash
    git tag vX.Y.Z -m "Что нового"
    git push origin vX.Y.Z
    ```

12. **Дождаться игроков.** `release.yml`: тесты → образ в GHCR → GitHub Release → выкладка на VPS
    через `deploy/deploy.sh` с дренажом матчей. Готово, когда публичный `/api/version` отдаёт новую
    сборку:

    ```bash
    curl -s <адрес игры>/api/version    # {"build":"vX.Y.Z+<sha7>","sim":"…","proto":N}
    ```

    Обычно 3–6 минут; ждать циклом с таймаутом 10 минут.

13. **Отчёт:** номер версии, ссылки на PR и GitHub Release, подтверждённый `build` и две-три строки
    «что проверить в игре» — приёмка идёт уже на боевом сервере.

Ревью ни у кого не запрашиваем: check `test` — единственный обязательный барьер.

### Какой номер

| Уровень | Когда | Пример |
|---|---|---|
| **patch** (`v0.2.1`) | исправления и правки, которых игрок не заметит как новое поведение | тексты, кэш, скорость |
| **minor** (`v0.3.0`) | игрок увидит новое поведение или новый элемент интерфейса; новые правила в `sim.js`; совместимые изменения протокола | WASD-управление, счётчик онлайна |
| **major** (`v1.0.0`) | несовместимый протокол (`proto` +1) или смена схемы поставки | — |

Правило разрешения споров: **если игрок заметит новое — minor, иначе patch.** Размер диффа не важен.

## Откат

Сломанный релиз чиним **вперёд**: новый patch-тег по тому же порядку. Состояния на диске нет,
специального отката не требуется.

Аварийный вариант для человека с доступом к VPS — выкатить предыдущий тег руками:

```bash
cd /opt/snowbrawl && ./deploy.sh v0.2.1
```

Старые образы лежат в GHCR.

## CHANGELOG

`CHANGELOG.md` ведём вручную по [Keep a Changelog](https://keepachangelog.com/ru/): при каждом
релизе заводим раздел с номером версии и датой. Раздел «Unreleased» не используем — тег ставится
сразу после влития, копить в нём нечего.
