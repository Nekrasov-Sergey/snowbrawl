# SnowBrawl — инструкция для агента

Браузерная PvP-игра в снежки. Сервер на Go отдаёт клиент, держит WebSocket и исполняет общую
симуляцию `web/sim/sim.js` через goja. Клиент вшит в бинарник, поэтому клиент и сервер всегда
одной сборки. Устройство проекта — [README.md](README.md), детали — в `docs/`.

## Перед коммитом

```bash
make test                      # go test -race ./...
gofmt -l .                     # должно быть пусто
make lint                      # golangci-lint, он же в CI
node --check web/client/<файл> # для каждого изменённого JS
```

Check `test` в CI прогоняет линтер, тесты, бенчмарк goja и сборку образа. Красный линтер блокирует
merge так же, как красный тест.

## Правила

- **`web/sim/sim.js` не менять без обсуждения с пользователем.** Это общий контракт клиента и
  сервера, любое изменение правил ломает совместимость. См. [docs/SIM_CONTRACT.md](docs/SIM_CONTRACT.md).
- **Версия сборки обязана меняться при каждом деплое.** Статика кэшируется браузером на час по ключу
  `?v=<build>`; сборка нумеруется `<тег>+<короткий SHA>`, это делает `release.yml`. Руками ничего
  подставлять не нужно, но и ломать этот механизм нельзя.
- **Секреты не выводить и не коммитить**: токен админки, `DEPLOY_*`, ключи VPS, токены GitHub.
- **Отвечать по-русски.**
- **Сетевые команды писать с `env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy`
  буквально**, не через переменную. Однажды переменная `$P` не раскрылась как команда, `git pull`
  молча не выполнился, и тег ушёл на старый main.
- **Боевой адрес игры** — https://snowbrawl.ru. Проверка деплоя: `/api/version`. IP сервера
  в репозиторий не пишем, он в памяти проекта.

## Как изменения попадают к игрокам

Полный порядок с командами — [docs/VERSIONING.md](docs/VERSIONING.md#релиз). Коротко:

1. Поток запускается **только явной командой** пользователя о доставке: «сделай релиз», «влей и
   задеплой», «доведи до игроков». Такая команда разрешает всё до пуша тега включительно, без
   промежуточных переспрашиваний. Без неё — ни одного git-действия; изменения остаются в рабочем
   дереве, и агент говорит об этом одной строкой в конце ответа.
2. Ветка `feat/<kebab>` или `fix/<kebab>` от свежего `origin/main`.
3. Изменения. Если их заметит игрок — новый раздел с датой в `CHANGELOG.md`.
4. Проверки выше, коммит по-русски в прошедшем времени («Изменил панель админа»), push.
5. PR через GitHub MCP (`gh` не установлен, токена в окружении нет).
6. Дождаться зелёного `test`. Красный — починить, максимум две попытки, потом остановиться и доложить.
7. Merge **только rebase**: `merge_method: "rebase"`. В репозитории включены rebase-only и линейная
   история, merge-коммиты запрещены, ветка удаляется автоматически.
8. `git pull --ff-only`, сверить HEAD с `sha` из ответа merge.
9. Тег `vX.Y.Z` на HEAD и push — если изменения доезжают до сервера. Правки только в `docs/**`,
   `README.md`, `CHANGELOG.md`, `CLAUDE.md`, `.github/**` тега не получают.
10. Дождаться деплоя: `/api/version` должен отдать `{"build":"vX.Y.Z+<sha7>"}`.
11. Отчёт: версия, ссылки на PR и Release, подтверждённый `build`, что проверить в игре.

Ревью ни у кого не запрашиваем. rc-теги не используем: minor — если игрок заметит новое поведение
или новый элемент интерфейса, иначе patch. Сломанный релиз чиним вперёд новым patch-тегом.
