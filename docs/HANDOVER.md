# Передача проекта заказчику

Цель: после передачи заказчик владеет всем — кодом, образами, сервером, доменом — и может
обновлять игру силами любого разработчика без участия автора.

## Что передаётся

| Артефакт | Где | Как передать |
|---|---|---|
| Исходный код (сервер + клиент + sim.js + документы) | GitHub `Nekrasov-Sergey/snowbrawl` (приватный) | Settings → Transfer ownership → аккаунт/организация заказчика |
| Docker-образы всех релизов | GHCR `ghcr.io/nekrasov-sergey/snowbrawl` | переезжают вместе с репозиторием; после передачи CI публикует под новым владельцем |
| Секреты деплоя (SSH-ключ, IP, путь) | GitHub Secrets репозитория | при Transfer сохраняются; лучше пересоздать ключ на стороне заказчика |
| Сервер (VPS) | Timeweb Cloud (или другой) | аккаунт заводит заказчик на себя; автор получает доступ по SSH |
| Домен | регистратор (reg.ru, Timeweb и т.п.) | покупает заказчик на себя |
| Документация | `docs/` в репозитории | вместе с кодом |

## Аккаунты, которые заводит заказчик

1. **GitHub** (бесплатно) — принять Transfer репозитория. Организация не обязательна.
2. **Хостинг** — Timeweb Cloud, тариф VPS 2 vCPU / 2 ГБ / 30 ГБ NVMe, Москва.
   Оплата картой РФ, ЮMoney, счётом для юрлиц. Ориентир **600–1200 ₽/мес**.
   Альтернативы: Selectel, Yandex Cloud, VK Cloud, Beget — любой VPS с Ubuntu 24.04 подойдёт.
3. **Домен `.ru`** — **200–400 ₽/год**. Необязателен для запуска: игра работает по IP.
   Нужен для HTTPS и красивого адреса.

Итого владение: **~1000 ₽/мес** без учёта работы разработчиков. Никаких платных сервисов
(БД, очереди, CDN) в проекте нет.

## Порядок передачи

1. Заказчик заводит GitHub-аккаунт и хостинг, создаёт VPS (Ubuntu 24.04), даёт автору
   SSH-доступ (или делает шаги RUNBOOK сам).
2. Автор выполняет «Первый запуск» из [RUNBOOK.md](RUNBOOK.md) на VPS заказчика,
   проверяет игру по IP.
3. Автор передаёт репозиторий (Transfer). Заказчик в Settings → Secrets заводит
   `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KEY`, `DEPLOY_PATH` — с этого момента любой
   пуш тега `v*` выкатывает новую версию автоматически.
4. Совместно делают контрольный релиз (например `v1.0.0`) и убеждаются, что он доехал.
5. Заказчик получает и хранит: `.env` с токеном админки, ссылку на админку, этот документ.
6. Демо-VPS автора гасится.

## Роли после передачи

- **Разработчик игры** правит `web/sim/sim.js` и `web/client/*` по
  [SIM_CONTRACT.md](SIM_CONTRACT.md), поднимает `SIM_VERSION`, тегирует релиз.
  Ему не нужно знать Go: тесты `go test ./internal/sim/` проверят его файл в goja.
  Сенсорное управление живёт в `web/client/touch.js` (стики) и `web/client/intent.js`
  (общий слой намерений для мыши и стиков); проверять на реальных Android и iPhone
  через pre-release тег `vX.Y.Z-rc.N` — он выкладывается на VPS, но не трогает `:latest`.
- **Любой Go-разработчик** правит сервер по [ARCHITECTURE.md](ARCHITECTURE.md) и
  [PROTOCOL.md](PROTOCOL.md).
- **Администратор** (может быть нетехнический) обновляет по RUNBOOK: одна команда
  `./deploy.sh vX.Y.Z` или вообще ничего, если настроен CI.

## Чего в проекте нет и почему

- Аккаунтов и рейтинга — по решению заказчика на MVP анонимный ник без БД. Задел: сессия
  уже имеет стабильный `playerId`, добавить SQLite и таблицу матчей можно без смены протокола.
- Чата — требует модерации.
- Параллельных версий при обновлении — обновление идёт через дренаж (до 3 минут ожидания).
- Prometheus/Grafana — при одной VPS и нетехническом владельце достаточно `/admin`.
- Защиты от читеров сильнее валидации ввода — игра для друзей.

## Юридическое

Персональные данные в смысле 152-ФЗ не обрабатываются: игрок указывает произвольный ник,
регистрации и e-mail нет. IP-адреса присутствуют только в технических логах сервера
(ротация 100 МБ).
