# Контракт `web/sim/sim.js` — для разработчика игры

`sim.js` — единственное место, где живут правила игры. Его исполняет браузер (оффлайн-режим)
и сервер (goja, для всех сетевых матчей). Всё, что здесь описано, сервер проверяет при
запуске (`sim.Compile`) и в тестах `internal/sim`.

## Что запрещено внутри sim.js

Сервер исполняет файл в чистом JS-окружении без браузера. Поэтому в sim.js **нельзя**:

- обращаться к `window`, `document`, DOM, Canvas, Web Audio, `localStorage`, `fetch`;
- использовать `performance.now()`, `Date.now()`, `new Date()`, `setTimeout`, `requestAnimationFrame`;
- использовать `Math.random()` — вместо него `state.rng.next()` (детерминированный, из seed);
- использовать ES-модули (`import`/`export`), `async/await` не нужен и не поддерживается для этого контракта;
- держать состояние в замыканиях модуля: всё состояние матча — внутри объекта `state`.

Можно: ES2015+ синтаксис (`let`, стрелки, деструктуризация, классы), `Math.*`, `JSON`,
обычные массивы/объекты. Файл — UMD-обёртка: в браузере создаёт глобал `SnowBrawlSim`,
в CommonJS — `module.exports`. Сервер ищет именно глобал `SnowBrawlSim`.

## Экспорт модуля

```js
SnowBrawlSim = {
  SIM_VERSION: '1.18.0',                // semver правил игры, показывается в админке и логах
  W, H, GRAVITY, HIT_Z, CHARGE_FULL_MS, KO_ANIM_MS,      // HIT_Z — с 1.6.0
  FREEZER_AURA_R, FREEZER_AURA_SLOW, FREEZER_AURA_RELOAD,      // с 1.8.0
  FROST_R, FROST_SLOW,                                         // с 1.8.0
  RELOAD_MS, AMMO_MAX, SHOT_GAP_MS,                            // AMMO_MAX, SHOT_GAP_MS — с 1.12.0
  PICKUP_RADIUS,                                               // с 1.13.0
  EXPLOSION_RADIUS, BUBBLE_REGEN_MS, WALL_LIFETIME_MS,         // с 1.8.0
  ARENAS, ROLE_STATS, SPECIALS, ABILITIES, BOT_LEVEL_NAMES, MODES,
  GAME_MODES: ['pvp','deathmatch','survival','defense'],   // с 1.3.0, deathmatch — с 1.17.0
  PVE_GAME_MODES: ['survival','defense'],      // с 1.17.0: какие из GAME_MODES — PvE
  DM_KILL_LIMITS: [5,10,15,20], DM_DURATION_MS,              // с 1.17.0, «Бой насмерть»
  CORPSE_MS, RESPAWN_IFRAME_MS,                              // с 1.17.0
  BOMBER_SPLASH_R, SLAM_R, SLAM_WINDUP_MS, BASTION_R, BASTION_ARC, BASTION_MS,
  HIT_TORSO_DY,                                              // с 1.18.0, рендер и обучение
  PVE_LEVEL_COUNT: 3,                          // с 1.3.0
  HERO_DESCRIPTIONS, ABILITY_HINT_TEXT, ALL_ROLES,
  makeRng(seed), shuffle(rng, arr),
  canHitTarget(obs, shooter, x, y, power) -> bool,   // с 1.1.1
  aimPath(obs, shooter, x, y, power, out?) -> path,  // с 1.6.0, луч прицела

  createMatch(config, seed) -> state,
  applyInput(state, playerId, input) -> bool,
  setBot(state, playerId, isBot) -> bool,
  tutorialSpawn(state, opts) -> id | null,     // с 1.4.0, только в матче обучения
  tutorialRemove(state, id) -> bool,           // с 1.4.0
  tutorialLock(state, on) -> bool,             // с 1.5.0, соперник держится на 1 HP
  step(state, dtSeconds) -> events[],
  snapshot(state) -> object,
  isOver(state) -> bool,
  winner(state) -> 'A' | 'B' | null,
  reason(state) -> '' | 'ko' | 'kills' | 'timeout' | 'cleared' | 'wiped' | 'objective' | 'expired'  // с 1.3.0, kills — с 1.17.0
}
```

Сервер обязательно использует: `SIM_VERSION`, `ARENAS.length`, `ALL_ROLES`, `GAME_MODES`,
`DM_KILL_LIMITS` (с 1.17.0: по нему `Program.KillLimitFor` нормализует лимит комнаты), `createMatch`, `applyInput`, `setBot`, `step`, `snapshot`, `isOver`, `winner`, `reason`.
Остальное — для клиента. Радиусы и сроки (`FREEZER_AURA_R`, `EXPLOSION_RADIUS`,
`BUBBLE_REGEN_MS` и соседние) экспортированы именно для него: по ним рисуются кольцо ауры
Фризера, вспышка взрыва и аура щитового пузыря, а обучение строит на них условия шагов.
До 1.8.0 эти числа были переписаны руками в `render.js` и `tutorial.js` и расходились с правилами.

### Луч прицела (с 1.6.0)

Две чистые функции, ничего не читающие и не меняющие в состоянии матча:

- `canHitTarget(obs, shooter, x, y, power) -> bool` (с 1.1.1) — долетит ли снежок до точки.
  Считает по «обычной» параболе, **без** роли и заряженного выстрела: по этой же оценке целятся
  боты, поэтому правки внутри меняют их поведение и требуют прогона детерминизм-тестов.
- `aimPath(obs, shooter, targetX, targetY, power, out?) -> path` (с 1.6.0) — путь снежка для луча
  прицела. В `shooter` можно передать бойца из снапшота как есть: читаются `x`, `y`, `role`
  (пассив Снайпера) и `armed` (заряженный настильный выстрел), поэтому луч совпадает с полётом и
  для них. Необязательный `out` — буфер вызывающего: точки переиспользуются между кадрами, ссылку
  симуляция не хранит (состояние в модуле запрещено).

```js
path = {
  n,                 // сколько точек заполнено в pts
  pts: [{ x, y, z, live, hit }],   // live — снежок ещё летит; hit — live и z <= HIT_Z,
                                   // то есть в этой точке снежок может задеть бойца
  endX, endY,        // где полёт кончился: падение, край арены или преграда
  blocked,           // упёрся в преграду раньше расчётной дальности
  flat,              // настильный выстрел (armed === 'snipe')
  travel, flight     // расчётная дальность (px) и время полёта (с)
}
```

`HIT_Z` — тот же порог, по которому снежок задевает бойца в `updateSnowballs`; кинематика броска
живёт в одном месте (`throwKinematics`), поэтому прицел и полёт не могут разъехаться. Правила игры
`aimPath` не меняет: это отдельная функция, состояние матча в неё не передаётся.

Область попадания (с 1.11.0, форма — с 1.13.0): модель бойца на клиенте (`web/client/rig.js`)
рисуется в полный рост — голова заметно выше игровой точки `(x,y)`, ноги заметно ниже, — поэтому
`hitTest` в `updateSnowballs` не круг радиуса `radius` и, с 1.13.0, не один прямоугольник. Для
всех 6 ролей игроков и PvE-типов `core`/`swarm` (они тоже рисуются ригом, просто ботами) — три
круга по контуру силуэта: голова (`HIT_HEAD_DY/R`), корпус (`HIT_TORSO_DY/R`), ноги
(`HIT_LEGS_DY/R`), все — доли `radius` от игровой точки вниз. Числа посчитаны руками из реальной
геометрии рига (`BW/BH/HR`, шаг ног, поза `idle`) и `RIG_SCALE=1.32` из `render.js` — `sim.js` не
может импортировать `rig.js` (там Canvas, тут исполняется и в goja), и не гонится за точностью
кадр-в-кадр во время бега/замаха, только разумный охват в нейтральной позе; круги специально
пересекаются, чтобы между ними не было мёртвой полосы. У PvE-голема (`tank`/`roller`/`boss` —
своя процедурная модель без рига, `drawGolem` в `render.js`) круги не подходят, там остался старый
прямоугольник (`HIT_BOX_DOWN/HALF_W/HALF_H`). Раньше снежок в ноги пролетал мимо кружка по центру
модели, потом прямоугольник накрывал и пустое место по бокам головы. На `canHitTarget`/`aimPath`
(порог 20 px по прицельной точке, к `radius` не привязан) это не влияет.

Размер моделей (с 1.13.0): `radius` всех 6 ролей игроков сделан буквально одинаковым (11, было
15/18/15/16/15/17) и уменьшен относительно прежнего — до этого Танк (18) и Щит (17) всё равно
рисовались крупнее остальных: унификация модели в `rig.js` (1.9.0) выровняла только пропорции
тела (`GEAR.big/w`), а не `radius`, от которого зависит масштаб рига. На небольшой карте
(900×560) визуально крупная модель делала попадание слишком лёгким; так как хитбокс (`hitTest`
выше), визуальный масштаб рига (`k = radius/46 * scaleMul * big` в `rig.js`) и позиции HP-бара/
ника (`Rig.topOf`/`bottomOf`, тоже от `radius`) выражены в долях `radius`, а не в пикселях,
правки констант достаточно — всё пересчитывается само. PvE-типы `core`/`tank`/`roller`/`boss`
уменьшены на 25% тем же приёмом (`swarm` не тронут — он и так маленький) и сохраняют собственные,
разные радиусы — это отдельная таблица, буквальная унификация касается только 6 ролей игроков.

### Способности (с 1.2.0)

У каждой роли один пассив (всегда) и один актив на Q (`input.kind = 'special'`, `(x,y)` —
прицел/направление). `ABILITIES[role] = { active: { id, cooldown, needsDir }, passive: <id> }`.
`SPECIALS[role]` сохранён для совместимости: `{ type: <id>, cooldown, needsDir }`.

| Роль | Пассив | Актив (id) |
|---|---|---|
| Раннер | при 1 HP скорость +20% | `dash` — рывок с неуязвимостью 0.25 с |
| Танк | попадание не сбивает замах, заморозка и оглушение вдвое короче (с 1.18.0) | `slam` — удар оземь: отбрасывает и оглушает врагов вокруг (с 1.18.0, до этого `taram`) |
| Снайпер | снежок быстрее/настильнее | `snipe` — следующий бросок по прямой на максимум |
| Бомбер | `splash` «Осколки»: каждый снежок бьёт по небольшой площади (с 1.18.0, до этого `sapper`) | `explosive` — взрывной снежок: большой взрыв, ломает ящики, стены босса и щит |
| Фризер | враги рядом на 50 % медленнее и дольше перезаряжаются | `frost` — следующий бросок оставляет наледь (−50 %), прямое попадание замораживает на 1 с |
| Щит | щитовой пузырь гасит одно попадание, реген 12 с | `bastion` — поворотный снежный щит спереди (с 1.18.0, до этого `wall`) |

Кулдауны активов (с 1.7.0, до этого были на треть длиннее): рывок 6 с, прицельный выстрел и
наледь 9 с, взрывной снежок 11.25 с, удар оземь 12 с, щит 13.5 с (как у прежней стены).

С 1.14.0 матч начинается с **полным кулдауном**: `createMatch`/`createPveMatch` ставят бойцам
`specialCooldown = ABILITIES[role].active.cooldown`, то есть способность в начале матча только
начинает заряжаться. Исключения — обучение (там способность готова сразу, см. ниже) и мобы волн
PvE с соперниками `tutorialSpawn`: они появляются с готовым активом, как и раньше. Респавн в PvE
кулдаун не трогает.

Пассив Фризера «Стужа» (с 1.8.0 усилен): в радиусе `FREEZER_AURA_R` = 110 (было 58) у врагов не
только скорость ниже на `FREEZER_AURA_SLOW`, но и медленнее на `FREEZER_AURA_RELOAD` = 25 %
течёт время перезарядки и кулдауна способности. Это растяжение времени в `updateTimers`, а не
штраф в момент броска: `specialCooldown` убывает медленнее, а абсолютные метки (`reloadUntil` —
пауза между выстрелами, `ammoAt` — срок текущего отделения боезапаса, с 1.12.0) сдвигаются вперёд,
пока боец в ауре — вышел из радиуса, и всё снова идёт обычным темпом. Главное здесь именно
`ammoAt`: с 1.12.0 темп стрельбы держит он, а не `reloadUntil`.
Оглушение аура не удлиняет: оно и так работает против пострадавшего. До 1.8.0 аура влияла только
на скорость и накрывала вчетверо меньшую площадь, поэтому Фризер не мешал ни Танку таранить, ни
Щиту ставить стены. Ориентиры для баланса: рывок Раннера — 118 px, обычный
бросок — 140…520, то есть выйти из зоны одним рывком от центра уже нельзя, а обстреливать Фризера
снаружи — можно. Границу радиуса проверяет `TestFreezerAuraBoundary`: остальные тесты ставят
Фризера вплотную и переживают любое значение.

#### Бой с 1.18.0: запинка, заморозка, удар оземь, щит, осколки

- **Запинка.** Обычное попадание (снежок, взрыв, сплэш) оглушает на `HIT_FLINCH` = 0,2 с
  при любом остатке HP и сбивает замах. До 1.18.0 было 0,5 с при 2 HP и 1 с при 1 HP, и
  стрелок успевал добить стоящую цель снежками из запаса. Лопнувший пузырь Щита — те же 0,2 с.
- **Заморозка.** Прямое попадание ледяным снежком Фризера оглушает на `FREEZE_STUN` = 1 с
  вместо прежних «оглушение + 1 с». Сбивает замах и замах удара оземь. Наледь на месте
  попадания остаётся. Событие `hit` несёт `freeze: true`. Отдельного поля в снапшоте нет:
  клиент помнит, что последнее оглушение ледяное, по событию.
- **Танк, «Броня».** Обычное попадание Танка не оглушает и замах не сбивает. Заморозка и
  оглушение от удара оземь на Танка вдвое короче (`TANK_CC_FACTOR` = 0,5). Правило по роли,
  поэтому касается и мобов PvE с ролью «Танк».
- **Танк, удар оземь (`slam`).** `special` ставит замах на `SLAM_WINDUP_MS` = 450 мс (событие
  `slamStart`). Пока идёт замах, Танк стоит и не начинает бросок: `chargeStart` отклоняется.
  Затем враги в `SLAM_R` = 160 px (без неуязвимых) отлетают и получают оглушение `SLAM_STUN` =
  1 с. Откат слабеет к краю: от `SLAM_KNOCK_NEAR` = 60 px вплотную до `SLAM_KNOCK_FAR` = 25 px
  на границе, линейно по расстоянию. Радиус — почти треть высоты арены, поэтому замах длиннее, чем
  у других способностей: из-под удара можно выйти. Откат и оглушение умножаются на
  `1 − knockResist`, у Танка оглушение ещё ×0,5. На каждого отброшенного — `knockback`. Вражеские снежки ниже `HIT_Z` в
  радиусе исчезают. Итоговое событие `{type:'slam', playerId, x, y}`. HP удар не снимает.
  Заморозка во время замаха отменяет удар. Снапшот: `slam` — сколько секунд до удара.
- **Щит, поворотный щит (`bastion`).** `special` поднимает щит на `BASTION_MS` = 2,5 с, сразу
  в сторону `(x,y)`. Затем щит доворачивает к прицелу бойца (`aimX/aimY`) по кратчайшей дуге не
  быстрее `BASTION_TURN` = 4 рад/с, то есть на 180° примерно за 0,8 с. Скорость и сектор подобраны
  на прототипе. `input.kind = 'aim'` при поднятом щите принимается и без замаха. Центр щита — корпус
  бойца (`y + radius·HIT_TORSO_DY`). Сектор ±`BASTION_ARC` = ±55°. Вражеский снежок не выше
  `BASTION_H` = 24, долетевший до `BASTION_R` = 30 px от центра в секторе, гибнет раньше
  проверки попаданий. Событие `{type:'shieldBlock', targetId, x, y}`. Ледяной снежок при этом
  оставляет наледь, взрывной взрывается. Так щит прикрывает и союзников за спиной. Взрыв
  активки Бомбера с центром в секторе поднятого щита бойца не ранит, но ломает щит (событие
  `bastionBreak`). Сплэш в секторе щита бойца не задевает и щит не ломает. Под щитом скорость
  ×`BASTION_SLOW` = 0,5, бросать можно. Щит снимается при KO и возрождении. Снапшот: `bst` —
  секунды до конца, `bsa` — текущий угол в радианах.
- **Бомбер, «Осколки».** Любой обычный снежок Бомбера при гибели (попадание, земля, стена,
  конец полёта) бьёт всех врагов в `BOMBER_SPLASH_R` = 26 px от точки, кроме цели прямого
  попадания. Событие `splash`, урон — `hit` с `splash: true`. Ящики сплэш не ломает.
  `EXPLOSION_RADIUS` активки вырос с 58 до 66.
- **Замедление Фризера.** Наледь (`FROST_SLOW`) и аура «Стужа» (`FREEZER_AURA_SLOW`) замедляют
  одинаково — на `FREEZER_SLOW` = 50 %, и не складываются: в наледи внутри ауры враг медленнее
  тоже ровно вдвое. До 1.18.0 наледь давала 40 %, аура 12 %, и вместе они перемножались.
- Стены Щита больше нет. `dynamicObstacles`, `walls` в снапшоте, `WALL_*` и `wallPlaced` остались
  для ледяной стены босса PvE. Таран (`TARAM_*`, `dash kind:'taram'`) тоже остался только у босса.
- Бот-Танк с готовым ударом идёт вплотную и бьёт, когда враг ближе `SLAM_R − 10`. Бот-Щит
  поднимает щит, когда враг замахивается или в него летит снежок, и держит щит на ближайшем враге.

Три уровня ботов: `config.players[].botLevel` (0 Лёгкий / 1 Обычный / 2 Сложный, по умолчанию 1)
масштабируют разброс прицела, паузы решений, шанс уворота и использования способности.
`BOT_LEVEL_NAMES` — подписи для UI. С 1.3.0 уровни раздвинуты: «Лёгкий» заметно мажет и вяло
реагирует, «Сложный» ослаблен относительно прежнего (был почти непобедим).

С 1.7.0 бот бросает при любом решении: раньше ветки «подошли ближе рабочей дистанции», «цель
слишком далеко» и «мало HP — за укрытие» выходили из ИИ до блока стрельбы, и бот вместо ответа
молча пятился (заметнее всего у Снайпера с его `minRange` 260). Теперь цель движения задаётся, а
затем всё равно проверяется бросок — боты в ближнем бою стали опаснее.

### Режим обучения (с 1.4.0)

`config.tutorial = true` — тот же PvP, но с тремя послаблениями для новичка. Режима **нет** в
`GAME_MODES`: сервер такие матчи не создаёт, обучение целиком идёт в браузере на оффлайн-драйвере.

- Состав может быть неполным: достаточно одного бойца, проверка «ровно `2*mode`» не применяется.
- Матч не заканчивается ни по KO, ни по таймеру: `checkWin` выходит сразу, `isOver` остаётся
  `false`. Завершает обучение клиент, когда пройден последний шаг.
- Ученик не выбывает: у бойцов команды `A` последнее HP не снимается, событие `hit` эмитится как
  обычно (оглушение, эффекты и звук на месте), события `ko` для них нет. Соперники стоят в команде
  `B` — их правило не защищает, добить их можно и нужно.
- Кулдаун любой способности не больше 2 с (`TUTORIAL_CD`, с 1.7.0): шаг про способность иначе
  превращался в ожидание до 13 секунд. Если у способности базовый кулдаун короче — берётся он.
  С 1.8.0 послабление действует **только на команду `A`**: с коротким кулдауном у соперника
  бот-Танк таранил (с 1.18.0 — бил бы оземь) каждые 2 секунды, и шаги «дайте сопернику попасть» превращались в непрерывное
  оглушение. Стартовый кулдаун 1.14.0 в обучении не ставится: шаг про способность считает её
  применённой по фронту роста `cd` в снапшоте, и ненулевой старт зачёлся бы ложно на первом кадре.
- `tutorialSpawn(state, {role, x, y, botLevel?, bot?})` добавляет бойца команды `B` и возвращает
  его id; `bot: false` — ИИ выключен, боец стоит на месте. `tutorialRemove(state, id)` убирает его
  вместе с его снежками. Вне матча обучения обе функции ничего не делают.
- Оживить и заморозить соперника по ходу — обычный `setBot`. Замораживать посреди замаха нельзя:
  `charging` останется висеть, сначала `applyInput(..., {kind:'cancelCharge'})`.
- `tutorialLock(state, true)` (с 1.5.0) распространяет правило «не ниже 1 HP» и на соперников
  команды `B`: пока замок стоит, соперника нельзя добить обычным попаданием. Замком распоряжается
  клиент: он держит его на шагах-упражнениях и снимает (`tutorialLock(state, false)`) на шаге
  настоящего боя.

### PvP-режим «Бой насмерть» (с 1.17.0)

`config.gameMode = 'deathmatch'` — тот же PvP (ровно `2*mode` бойцов, команды A/B, те же
стартовые точки), но выбитый боец не выбывает до конца матча:

- **Возрождение.** `updateDeathmatch` (в `step` перед `checkWin`) поднимает бойца, когда с `koAt`
  прошло `CORPSE_MS` = 3000 мс — ровно за столько клиент растапливает труп (render.js берёт
  длительность таяния из `Sim.CORPSE_MS`, отсчёт «Возрождение через 3, 2, 1 с» — оттуда же). Точка — случайная на своей базе (`baseSpawnPoint`: `x` в
  ±50 от 160 у A и от `W-160` у B, `y` в 110..450, не внутри препятствия — до 20 попыток), сброс
  общий с PvE (`respawnFighter`): 3 HP, полный запас, снятые замах, рывок и взведённая
  способность, пузырь Щита, неуязвимость `RESPAWN_IFRAME_MS` = 3 с. Событие
  `{type:'respawn', id, x, y}`. Время до возрождения клиент считает сам: `koAt + CORPSE_MS`.
- **Лимит.** `config.killLimit` — одно из `DM_KILL_LIMITS` (5/10/15/20), иначе значение по
  умолчанию для размера: `DM_KILL_LIMITS[mode-1]`. Лежит в `state.killLimit` (0 во всех других
  режимах) и в снапшоте как `killLimit` (только в deathmatch).
- **Исход** (`checkWin`): счёт команды — сумма `kills` её бойцов (то же `k` в снапшоте, клиент
  считает счёт так же). Набрала `killLimit` — победа, `reason = 'kills'`; если лимит в одном подшаге
  добрали обе, решает счёт, при равенстве ничья с той же причиной. Запасной таймер —
  `DM_DURATION_MS` = 10 мин (если `durationMs` не задан): по нему побеждает больший счёт,
  `reason = 'timeout'`, при равенстве `winner = null`. Правило «команда вымерла» здесь не действует.
- **Боты** в deathmatch выбирают цель без неуязвимости и берут неуязвимую, только если других нет
  (`findNearestEnemy`). `canHitTarget` не менялась.

Общие правки 1.17.0, которые касаются и других режимов:
- таран Танка (`applyTaram`) больше не сбивает и не оглушает неуязвимого (`iframeUntil`: рывок
  Раннера, возрождение) — иначе вставшего тут же валили у базы;
- возрождение члена пати в PvE идёт через тот же `respawnFighter`: теперь оно тоже снимает
  замах, рывок и взведённую способность, а точка появления не попадает в препятствие;
- `PVE_RESPAWN_MS` (2.5 с) удалена: член пати встаёт через `CORPSE_MS` от `koAt`, как и в
  deathmatch, а трупы бойцов и мобов тают за те же 3 с (было 4);
- `PVE_RESPAWN_IFRAME_MS` переименована в `RESPAWN_IFRAME_MS`, `PVE_BASE_HALF_W`/`PVE_BASE_MARGIN_Y`
  — в `BASE_HALF_W`/`BASE_MARGIN_Y`, значения прежние.

### PvE-режим «Волны» (с 1.3.0)

`config.gameMode` (`'pvp'` по умолчанию, `'survival'`, `'defense'`) переключает тип матча.
В PvE вся пати — команда `A` (люди + союзные боты, `botLevel` из `config.difficulty` 0..2),
команду `B` создаёт волновой планировщик внутри `step` по ходу матча. `config.campaign`
(по умолчанию `true`) — кампания из `PVE_LEVEL_COUNT` уровней с боссами; `false` — сразу
бесконечный эндлесс. `config.pve = { levels?, waves? }` урезает кампанию для тестов.

- Врагов ≤ 24 одновременно; спавн от правого края, растянут во времени.
- Жизни пати (`players[].lives`, старт 3) пополняются в начале волны, все возрождаются;
  выбывший в бою возрождается, пока есть жизни. С 1.17.0 — когда растаял труп, через
  `CORPSE_MS` = 3 с от `koAt` (было 2.5 с от момента, когда `updatePve` заметил выбывание), в
  случайной точке базы не внутри препятствия и с неуязвимостью `RESPAWN_IFRAME_MS`.
- Между волнами пауза 12 с (`pve.phase = 'between'`, `pve.nextInMs`).
- Исход (`reason(state)` и событие `matchEnd`): `cleared` — кампания пройдена; `wiped` —
  вся пати выбита без жизней; `objective` — в «Защите» разбит снеговик; `expired` —
  абсолютный потолок 60 мин. В кампании `wiped`/`objective` не заканчивают матч, а
  перезапускают уровень с первой волны; в эндлессе — заканчивают.
- Типы врагов: `core` (снежколёт), `swarm`, `tank`, `roller` (урон контактом у `swarm`/`roller`),
  `boss` (`golem` / `blizzard` / `yeti`, две фазы). С 1.5.0 рядовые враги ослаблены: `core` больше
  не берут роль «Раннер» (не расстреливают очередями), `tank` — 5 HP. С 1.9.0 `swarm` ослаблен ещё
  раз (был слишком силён числом и скоростью): скорость 198→150, кулдаун контактного урона
  0.8→1.4 с (`ENEMY_STATS[type].contactCd`, по умолчанию `CONTACT_DAMAGE_CD`; у `roller` не менялся).
  События: `waveStart`, `waveCleared`,
  `enemySpawn`, `bossPhase`, `contactHit`, `objectiveHit`, `levelStart`, `levelRestart`,
  `partyDown`, `partyRespawn` — все опциональны, клиент игнорирует незнакомые.

  Снеговик в «Защите» (с 1.15.0): за каждую зачищенную волну подлечивается на `SNOWMAN_WAVE_HEAL`
  = 3 HP (кап — свой `maxHp`, 40) — до этого HP не восстанавливался между волнами вовсе, и долгий
  забег до босса было почти невозможно доиграть, если снеговик потрёпан ранними волнами. Правило —
  сразу после `waveCleared`, до паузы между волнами.

  Починка `koAt` у «Кома» (`roller`, с 1.15.0): при самоубийстве об стену/препятствие после рывка
  (`moveCharacter`) и при смерти от собственного контактного урона (`updateContactDamage`) `koAt`
  не выставлялся (оставался 0 по умолчанию из `makeChar`) — с этим полем клиент считает прогресс
  анимации таяния трупа (`snap.time - (p.koAt || snap.time)`), и `0` в `koAt` через `||`-фолбэк
  каждый кадр подставлял текущее время, из-за чего прогресс навсегда застревал на нуле: труп не
  таял и не убирался по таймеру, как у остальных PvE-врагов. Оба места теперь ставят
  `koAt = state.time`, как и обычная смерть от снежка (`applyHit`).

  Возрождение члена пати (с 1.16.0): `pveSpawnPoint` раньше выдавала фиксированную точку на
  игрока (детерминированный слот по `spawnYs`) — противник зажимал её и фармил фраги. Теперь
  это равномерно случайная точка в прямоугольнике базы: `x` в `±PVE_BASE_HALF_W` (50) вокруг
  цели (160 обычно, 180 в «Защите»), `y` в `PVE_BASE_MARGIN_Y..H-PVE_BASE_MARGIN_Y` (110..450).
  Неуязвимость после возрождения увеличена с 1.2 до 3 с (`PVE_RESPAWN_IFRAME_MS`, тот же
  механизм `p.iframeUntil`, что и у рывка). Начальная расстановка пати при старте волны/уровня
  (`spawnYs`, отдельно от `pveSpawnPoint`) не изменилась.

Боезапас (с 1.12.0): у бойца `AMMO_MAX` = 3 заряда, `chargeStart` отклоняется при `p.ammo < 1`
и пока `state.time < p.reloadUntil` — теперь это короткая пауза `SHOT_GAP_MS` = 250 мс между
двумя выстрелами из запаса (без неё три снежка уходили одним залпом в упор). Отделения
заполняются **по одному**, срок текущего — `p.ammoAt`, длительность `RELOAD_MS[role] × 1.4`
(Раннер 700 … Снайпер 2240 мс): множитель нужен, чтобы запас в три выстрела не был чистым
усилением всех ролей. Бросок не сбрасывает уже идущее заполнение. Правило общее для людей и
ботов. Мобы PvE запас не тратят: у них `reloadUntil` остаётся прежним кулдауном по роли
(`RELOAD_MS`), иначе пауза в 250 мс втрое ускорила бы стрельбу волн; босс кидает по своему
`bossTimer`. Событие `reloadDone`
означает «появился заряд» и несёт `ammo`; событие `throw` несёт `ammo` вместо прежнего `reload`.
До 1.12.0 выстрел был один, а пауза равнялась целому `RELOAD_MS`.

Разрушаемые укрытия: у части препятствий `ARENAS[].obstacles[]` есть `hp` (снимается только
взрывом Бомбера). Зона льда карты «Река»: `ARENAS[].ice = { y0, y1, speedup }` — полоса `y0..y1`,
где боец разгоняется (`speed *= 1+speedup`) и скользит: направление довора­чивает к цели с
ограниченной резкостью (`ICE_STEER`, 1/с) вместо мгновенного разворота — эффект «неповоротливости»
на льду. До 1.9.0 поле называлось `slow` и наоборот замедляло; клиент от значения `.slow`/`.speedup`
не зависит (использует только `y0`/`y1` для рендера полосы).

### `createMatch(config, seed)`

```js
config = {
  gameMode?: 'pvp'|'deathmatch'|'survival'|'defense',   // по умолчанию 'pvp' (с 1.3.0; deathmatch — 1.17.0)
  mode: 1|2|3|4,                 // PvP — размер команды; PvE — размер пати
  arenaIndex: 0..ARENAS.length-1, // PvP; в PvE арену задаёт уровень кампании
  durationMs?: 300000,           // PvP — таймер матча (5 мин, потом ничья; в deathmatch 10 мин,
                                 // потом победа по счёту); PvE игнорируется
  killLimit?: 5|10|15|20,        // deathmatch — выбиваний для победы, иначе DM_KILL_LIMITS[mode-1] (с 1.17.0)
  difficulty?: 0|1|2,            // PvE — ручка сложности (с 1.3.0)
  campaign?: true,               // PvE — кампания (по умолч.) или эндлесс (с 1.3.0)
  pve?: { levels?, waves? },     // PvE — урезание кампании для тестов (с 1.3.0)
  players: [                     // PvP — ровно 2*mode; PvE — 1..4, все team 'A'
    { id: 'p1a2b3c4', team: 'A', role: 'Бомбер', bot: false, nick: 'Сергей' },
    { id: 'bot1',     team: 'B', role: 'Танк',   bot: true,  nick: 'Бот 1', botLevel: 2 },
  ]
}
```

`seed` — uint32; при одинаковых seed и одинаковой последовательности `applyInput`/`step`
результат должен совпадать байт в байт (проверяется тестом `TestDeterministic`).
Бросать исключение при плохой конфигурации можно и нужно: сервер залогирует и не создаст матч.

### `applyInput(state, playerId, input)`

`input = { kind, x, y, power? }`, координаты уже в системе арены. Виды:

| kind | смысл |
|---|---|
| `move` | цель перемещения |
| `chargeStart` | начать замах, (x,y) — прицел |
| `aim` | обновить прицел во время замаха; с 1.18.0 — и при поднятом щите Щита, без замаха |
| `throw` | бросить; `power` 0..1 от клиента; sim сверяет со своим таймингом (допуск 0.25) |
| `cancelCharge` | отменить замах без броска (с 1.1.0; стик вернулся в мёртвую зону, курсор отпущен над бойцом) |
| `special` | способность (Q) |

Возвращает `true`, если ввод принят. Неизвестный игрок, мёртвый боец, оглушение — `false`,
без исключений. Значения из сети надо считать враждебными: зажимать координаты, проверять `isFinite`.

### `setBot(state, playerId, isBot)`

Переключает управление бойцом на ИИ и обратно. Сервер зовёт при дисконнекте, AFK,
возвращении игрока. Должно работать в любой момент матча.

### `step(state, dt)`

Продвигает матч на `dt` секунд (сервер зовёт с 1/20). Внутри физика идёт подшагами ≤ 1/60 с,
чтобы поведение не зависело от частоты тиков. Возвращает массив событий шага:

```
{type:'chargeStart', playerId}
{type:'throw', playerId, power, special: null|'explosive'|'freeze'}
{type:'hit', targetId, x, y, freeze, hp, splash?}   // попадание, боец жив; splash — с 1.18.0
{type:'ko', targetId, x, y}                    // третье попадание
{type:'wallHit', x, y}  {type:'miss', x, y}  {type:'explosion', x, y}
{type:'special', playerId, special}  {type:'wallPlaced', playerId}   // wallPlaced с 1.18.0 — только босс
{type:'dash', playerId, kind:'dash'|'taram'}   {type:'knockback', targetId, x, y}   // с 1.2.0; taram — только босс
{type:'slamStart', playerId}  {type:'slam', playerId, x, y}                         // с 1.18.0, Танк
{type:'bastion', playerId}  {type:'bastionBreak', playerId}  {type:'shieldBlock', targetId, x, y}  // с 1.18.0, Щит
{type:'splash', x, y}                                                               // с 1.18.0, Бомбер
{type:'frost', x, y}   {type:'bubblePop', targetId, x, y}   {type:'bubbleReady', playerId}
{type:'obstacleHit', x, y}   {type:'obstacleBreak', x, y}
{type:'reloadDone', playerId, ammo}   // с 1.12.0: появилось отделение боезапаса, ammo — сколько стало
{type:'throw', ..., ammo}             // с 1.12.0 вместо reload: сколько зарядов осталось
{type:'matchEnd', winner: 'A'|'B'|null, reason?}   // reason — с 1.3.0 (PvE)
// PvE (с 1.3.0): waveStart, waveCleared, enemySpawn, bossPhase, contactHit,
//                objectiveHit, levelStart, levelRestart, partyDown, partyRespawn
{type:'respawn', id, x, y}            // с 1.17.0, deathmatch: боец встал на своей базе
```

События — единственный источник для звука и эффектов на клиенте. Новые события добавлять
можно свободно: клиент игнорирует неизвестные.

### `snapshot(state)`

Сериализуемый объект для рендера и сети (через `JSON.stringify`, поэтому без функций и циклов):

```
{ v, tick, time, timeLeft, mode, arena, ice, over, winner,
  gameMode, reason,                                           // с 1.3.0
  players: [{ id, team, role, nick, bot, x, y, hp, stun, koed, koAt, hitAt, k,
              moving, anim, charging, power, aimX, aimY, special, cd,
              armed, iframe, dash, bubble, slow, rl, am,       // armed…rl — с 1.2.0, am — с 1.12.0
              bb,                                              // с 1.8.0, заряд пузыря Щита
              slam, bst, bsa,                                  // с 1.18.0: замах удара, щит (с, угол)
                                                               // k — с 1.10.0, счёт выбитых
              lives?, et?, mhp?, bk?, bph? }],                 // PvE, с 1.3.0
  balls:   [{ id, x, y, z, r, team, ex, fr, sn }],
  walls:   [{ x, y, w, h, team, hp, maxHp, ttl, life }],
  destr:   [{ i, type, x, y, w, h, r, mat, hp, maxHp }],      // разрушаемые укрытия арены
  fx:      [{ id, kind:'frost', x, y, r, team, ttl, life }],  // зоны на земле
  pickup?: { x, y, r },                                       // «жизнь» на карте, с 1.12.0
  killLimit?,                                                 // deathmatch, с 1.17.0
  pve?: {  objective, campaign, endless, level, levelCount, wave, waveCount,   // PvE, с 1.3.0
           enemiesLeft, phase:'fighting'|'between', nextInMs, wavesSurvived,
           bossHp, bossMax, objHp?, objMaxHp?, objX?, objY?, objR? } }
```

`rl` (с 1.12.0 — иной смысл) — доля оставшейся паузы между выстрелами от `SHOT_GAP_MS`,
**зажата в 1**: в ауре Фризера остаток может превысить базовое время (см. «Стужа» выше). Клиент
по этому полю ничего не рисует, а решает, поставить ли нажатие в очередь. До 1.12.0 это была
доля перезарядки от `RELOAD_MS`, и по ней рисовалась дуга вокруг бойца.

`am` (с 1.12.0) — боезапас: целая часть — полные отделения (0..`AMMO_MAX`), дробная — заполнение
текущего. Клиент рисует по нему полоску из трёх отделений под своей полоской здоровья и по нему
же (`am >= 1`) решает, можно ли начать замах. Поле есть у каждого бойца по той же причине, что
`bb`. Интерполировать его нельзя: на выстреле значение прыгает вниз, и линейное сглаживание
показало бы съезжающую назад заливку.

`bb` (с 1.8.0) — доля оставшегося восстановления щитового пузыря, 0..1; ноль у всех, кроме Щита
с потушенным пузырём. Реген в `updateTimers` требует одновременно 12 с с момента хлопка и 12 с без
реального урона, поэтому `bb` считается по **позднему** из двух сроков — иначе свечение у бойца
под обстрелом врало бы. Поле присутствует у каждого бойца, а не только у Щита: клиент переиспользует
объекты бойцов при интерполяции, и пропущенный ключ сохранял бы прошлое значение.

`k` (с 1.10.0) — сколько соперников выбил этот боец за матч; растёт в `applyHit` у владельца
снаряда или взрыва (`snowballs[].ownerId`) и только при попадании по чужой команде. Контактный
урон мобов PvE и самоподрыв «катка» фрага никому не дают — бить некому. Счётчик переживает
возрождение в PvE и, раз он в снапшоте, одинаково верен после реконнекта и у зрителя. Событие
`ko` с 1.10.0 несёт `killerId` (может быть `null`) — им пользуется тот, кому нужен сам факт, а не
итог. Клиент показывает эти числа только на плашке итогов.

Клиент интерполирует `players[].x/y/anim/power` и `balls[].x/y/z` по `id` между снапшотами —
поэтому у снежков **обязательно** стабильный `id`. Округление до десятых сделано ради
размера JSON: снапшот 4×4 — около 2 КБ, 20 раз в секунду на игрока.

Подбираемая «жизнь» (с 1.13.0): `updatePickups` держит не больше одного `state.pickup` сразу
(`{x, y, expiresAt}`) — общая механика для PvP и PvE, недоступна только в обучении. Появляется
через случайные `PICKUP_RESPAWN_MIN..MAX` (15–30 с) после того, как предыдущая исчезла (подобрали
или истёк `PICKUP_LIFETIME_MIN..MAX`, 30–40 с без подбора), в случайной точке арены не внутри
препятствия (до 20 попыток, `pickPickupSpot`). Подбирает касанием (`radius` бойца + `PICKUP_RADIUS`)
любой живой боец из `state.players` — человек, бот или PvE-моб одинаково, это один общий массив.
Лечит 1 HP с капом на `maxHp`: боец на полном HP предмет не трогает, он остаётся для другого.
Раненые боты и мобы (кроме `swarm`/`roller` — у них по дизайну нет манёвров, см. `updateSwarmAI`)
идут к жизни специально, если она не дальше `PICKUP_SEEK_R`, но продолжают отстреливаться по пути
(`tryShoot(true)`), как и при обычном отходе в укрытие.

## Обязательные правила для сервера

- **Матч должен заканчиваться.** В PvP таймер `durationMs` с ничьёй обязателен: без него
  два спрятавшихся игрока держат матч и память сервера вечно. В deathmatch это `DM_DURATION_MS`. В PvE ту же роль играет
  абсолютный потолок 60 мин (`reason = 'expired'`).
- **Боты должны уметь играть сами**: сервер добирает ими команды и заменяет отключившихся.
- `isOver`/`winner` должны соответствовать событию `matchEnd`.

## Что изменено относительно прототипа

Порт из `SnowBrawl_prototype.html` точный, кроме:

1. `performance.now()` → `state.time` (мс с начала матча), `Math.random()` → `state.rng`.
2. Звук, частицы, тряска, снежинки, следы снежков вынесены в клиент и управляются событиями.
3. Физика подшагами ≤ 1/60 с (иначе на 20 тиках снежок пролетает окно попадания).
4. **ИИ: сила броска подбирается по дистанции** (`(dist+20-140)/380`), а не `0.35+dist/500`.
   В прототипе боты систематически перебрасывали цель и за 80+ секунд не попадали друг в друга
   ни разу; для AI Fill это неприемлемо.
5. **ИИ: обход застревания** — если с прошлого решения бот не сдвинулся, а цель далеко,
   он уходит вбок. В прототипе бот в 1×1 навсегда застревал за колонной у точки появления.
6. После попадания замах сбрасывается (по ТЗ боец теряет возможность атаковать).
7. Добавлены таймер матча (5 мин → ничья), `setBot`, `id` у снежков, события.

## Как проверить свои изменения

```bash
go test ./internal/sim/        # компиляция в goja, детерминизм, матч ботов завершается, ввод
make bench                     # производительность: должно оставаться < 30 % ядра
make dev                       # и открыть http://localhost:8080 → «Тренировка с ботами»
```

При смене правил поднимайте `SIM_VERSION`. Формат снапшота/событий — часть контракта с
клиентом (`web/client/render.js`), а не с сервером: сервер их не читает.
